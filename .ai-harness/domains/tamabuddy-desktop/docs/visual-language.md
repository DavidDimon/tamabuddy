# Desktop visual language

The implemented interface uses a compact retro-digital presentation: dark surfaces, cyan status text, monospace typography, small framed controls, and mascot-specific accent colors. Preserve that recognizable direction while improving hierarchy, spacing, state feedback, and polish.

Visual work must begin with the actual app states rather than a generic landing-page pattern. Review at least onboarding, active care, settings, destructive confirmation, loading/error feedback, and reduced-motion behavior. Validate the native window as well as browser previews.

Prefer tokens for repeated color, spacing, type, border, and motion decisions. Motion should explain state change or reaction, use transform/opacity when practical, and respect `prefers-reduced-motion`. Decorative treatment must not obscure meters, commands, messages, focus, or disabled state.

External design skills provide options, not product requirements. The Tamabuddy brief, accessibility constraints, existing mascot identity, and tested behavior take precedence.

The pinned `redesign-existing-projects` skill supplies an audit vocabulary for typography, surfaces, interaction states, semantic markup, and polish. Apply only findings demonstrated in the actual desktop states. Ignore landing-page assumptions such as marketing sections, stock imagery, legal footers, scroll choreography, or wide-screen content containers unless a separate public showcase explicitly needs them.
